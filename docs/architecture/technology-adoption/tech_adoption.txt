## Recommended coherent agent architecture

```text
Master (custom) → Agent Runtime interface (custom)
                      ↓
              PydanticAI specialists (default)
                      ↓
         optional LangGraph graph for long bring-up pipelines
                      ↓
         tools only via Device Broker client (never raw host)
                      ↓
         Broker → MCP SDK transport + policy + audit
```

- **PydanticAI** = typed agent definitions, tools, structured I/O, MCP client usage.  
- **LangGraph** = optional durable stateful workflows (human approve, retry, resume).  
- **Do not** run CrewAI + ADK + LangGraph + PydanticAI as peer orchestrators.

---

## Critical path (next implementation priorities)

1. **PoC:** official MCP SDK wrapping existing Device Broker policy (no L1 ceiling raise).  
2. **Agent Runtime v0** + 2–3 PydanticAI specialists (`research`, `firmware`, `lab`) behind Master.  
3. **LiteLLM SDK** behind Model Gateway (Ollama + one cloud provider).  
4. **Engineering OS Phase 5:** controlled serial read + profile-selected build (L2); flash remains L3+approve.  
5. Observability PoC after agents exist.

---

## Explicitly do **not** do next

- Rewrite Mark / Dot / Project OS / Broker policy from scratch.  
- Always-on LangSmith/Phoenix/n8n/LiteLLM-proxy stack on the Pi.  
- Auto-flash or continuous USB monitoring.  
- Hardcode Arduino as default board.  
- Introduce a second project database or second Master.  
- Adopt A2A “everywhere” for in-process calls.

## 6. Architectural conflicts to avoid

1. Letting LangGraph or n8n own project truth.  
2. Letting MCP clients call host tools without Broker.  
3. Running heavy always-on stacks (proxy + tracer + n8n + Ollama) concurrently on 8 GB without budgeting.  
4. Treating Phase 4 “Arduino probable” profile match as a hardcoded default board (it is evidence-based only).

---

## 7. Dependency tension (verified research)

Official MCP Python SDK v2 (`mcp` on PyPI) requires Python ≥3.11 (**OK**) and recent Pydantic/httpx2 stack. PYRA currently pins `pydantic>=2.6,<3` and `httpx>=0.27`. **Migration needs a dependency PoC** before REPLACE.

---

## 8. Summary judgment

Foundation is solid and coherent with Alternative C. The largest missing product layer is **Agent Runtime + specialists**, then **L2/L3 engineering execution** behind Broker. Protocol/tooling upgrades (MCP SDK, LiteLLM, Playwright) should be **adapters**, not rewrites.

## 3. Communication flows

**User request:** Mark → Dot → Master → (Project OS context) → capability OR Agent Runtime → Broker → tools → evidence → speech/HUD.

**Tool call:** Agent proposes tool → Runtime enforces allowlist/max_level → Broker validates → execute → audit → structured result → agent (untrusted wrap as needed).

**Approval (L2/L3):** Broker/Master issues `NeedsConfirm` → Mark confirm → token validated server-side → execute.

**Failure:** Tool/model failure → agent `blocked|failed` → Master summarizes; Project OS task state updated; no silent success.

| Agent scratch | Optional non-authoritative; never replaces Project OS |
| LangGraph checkpoints | Separate graph DB/files **scoped to workflow**, not Project OS replacement |
| Secrets | Env/keyring — never Project memory or traces |

**Always-on:** Mark, Master+Dot+Broker+Project OS, Ollama (as today).

**Optional:** n8n, tracer UI, Renode — prefer another host or start/stop.

### ADR-T01 — PydanticAI as primary specialist agent framework

- **Status:** Proposed (adoption pack)  
- **Context:** Need typed specialists; avoid CrewAI/ADK overlap; Python 3.13.  
- **Options:** PydanticAI; LangGraph-only agents; CrewAI; ADK; custom loops only.  
- **Decision:** **ADOPT PydanticAI** behind PYRA Agent Runtime.  
- **Rationale:** MIT, MCP support, structured I/O, fits existing Pydantic stack.  
- **Consequences:** Learn PydanticAI; wrap all tools via Broker.  
- **Rejected:** CrewAI core; ADK as primary.

### ADR-T02 — LangGraph for durable engineering pipelines only

- **Status:** Proposed  
- **Context:** Bring-up needs HITL, resume, multi-step evidence.  
- **Decision:** **EVALUATE then ADOPT LangGraph** for Eng OS pipelines — not for Master or Project OS.  
- **Rejected:** LangGraph as universal orchestrator.

### ADR-T03 — Official MCP SDK replaces custom transport

- **Status:** Proposed (gated on PoC-1)  
- **Context:** Minimal JSON-RPC lacks full protocol; SDK is MIT and maintained.  
- **Decision:** **REPLACE** custom MCP server with official SDK **after** dependency/security PoC.  
- **Invariant:** Broker remains permission authority.  
- **Risk:** pydantic/httpx2 upgrade.

### ADR-T04 — Defer A2A

- **Status:** Proposed  
- **Context:** Internal agents are in-process; A2A adds surface area.  
- **Decision:** **DEFER** until external/remote agents required.  
- **Note:** MCP ≠ A2A.

### ADR-T05 — LiteLLM SDK behind Model Gateway; defer proxy

- **Status:** Proposed  
- **Context:** Need Gemini/OpenAI/Ollama routing; Pi RAM limited.  
- **Decision:** Adopt **LiteLLM as library** behind ModelGateway; defer always-on proxy.  
- **Rejected:** Second bespoke multi-provider client long-term.

### ADR-T06 — Observability: OTEL first; one UI later

- **Status:** Proposed  
- **Context:** Need traces without starving Pi. Phoenix is ELv2.  
- **Decision:** Instrument with OpenTelemetry; evaluate **one** of Phoenix/Langfuse later.  
- **Rejected:** Deploying both UIs.

### ADR-T07 — Hardware tools are Broker tools, not agent-native

- **Status:** Proposed  
- **Context:** PlatformIO/pyOCD/etc. are mature.  
- **Decision:** Integrate as allowlisted Broker executions with levels; Eng OS owns workflow.  
- **Rejected:** Agents shelling out freely; custom flash engines.

### ADR-T08 — Knowledge: Docling before vector DB

- **Status:** Proposed  
- **Decision:** Evaluate Docling for datasheets; defer Qdrant/Chroma until corpus requires.  
- **Rejected:** Standing up vector DB in foundation phase.
